    1. Vision¶

    Every AI agent product ships a v1.0 system prompt and iterates via ad-hoc prompt edits. evo-skillopt makes that iteration disciplined: epochs, batches, validation gates, git-tracked audit trails — the same rigor a neural-network trainer takes for granted, applied to natural-language skill files.

    The compounding advantage is not the code (open source). It is the accumulated evaluation sets and evolved skill artifacts a team builds up inside their own repo, over time.

    2. What evo-skillopt is¶

    One sentence: A productized wrapper around SkillOpt (arXiv:2605.23904) that exposes text-space skill optimization as an HTTP service, callable from any agent runtime in any language.

    Elevator pitch:

    Your customer-support bot answers 500 tickets a week. Every ticket is a training signal. evo-skillopt takes those signals, runs SkillOpt training against your bot's held-out eval set, and ships an updated skill.md every Monday — only if it beats the previous one. If it doesn't, we roll back. Never touches model weights. Typical cost: single-digit dollars per evolution in LLM tokens.

    Not: a new training algorithm · a new LLM · a prompt IDE · a standalone eval framework.

    Is: the operations layer that closes the loop between (a) real production signals and (b) the SkillOpt training loop, at inference-time cost, with git-tracked audit trails.

    3. Architecture¶

       your agent runtime          evo-skillopt worker           SkillOpt core
   (any language)              (Python HTTP · stdlib)        (vendored MIT)
        │                            │                             │
        │  POST /train               │                             │
        │  {bot_id,                  │                             │
        │   skill_path,              │                             │
        │   skill_version,           │                             │
        │   eval_split_dir,          │                             │
        │   config,                  │                             │
        │   num_epochs,              │                             │
        │   gate_min_improvement}    │                             │
        │───────────────────────────►│                             │
        │                            │ subprocess.run(train.py) ──►│
        │                            │                             │  rollout
        │                            │                             │  reflect
        │                            │                             │  aggregate
        │                            │                             │  select
        │                            │                             │  update
        │                            │                             │  gate
        │                            │◄──── history.json ──────────│
        │◄──────── JSON response ────│  (delta, next_version, dir) │

    6. Use-cases catalog¶

    Each pattern is described in USE_CASES.md with signal wiring, cadence, ROI math, and guardrails. Summary here:

    # Pattern Signal source ROI shape
    1 Customer-support bot Ticketing CSAT + resolution outcome Deflected human hours
    2 Outbound sales-reply assistant CRM reply/meeting-booked events Meta-knowledge → team playbook
    3 Docs / API assistant Thumbs-up/down + follow-ups Deflected support + activation lift
    4 Community moderator Human-mod overrides Mod hours saved + retention
    5 Adaptive tutor Exercise completions + progress Retention + upsell
    6 Group-chat summarizer Thumbs on digests Attention saved / week
    7 Async standup assistant Digest-response opens Meeting hours avoided
    8 Content moderator with escalation rubric Precision/recall vs held-out set False positives ↓
    9 Interview / role-play coach User rating on realism + usefulness Upsell trigger
    10 Meeting-notes assistant Human edits after generation Editing time ↓

    Each use case must document, in order:

    1. What — one sentence
    2. skill.md structure — 30–50 lines of behavior + guardrails
    3. eval/held_out.json structure — 20–30 examples w/ reward_criteria
    4. Signal wiring — table of events → fitness_delta
    5. Cadence — how often evolution triggers
    6. ROI math — baseline vs post-evolution with concrete numbers
    7. Guardrails — what evolution can NEVER change

    9. KPIs¶

    Product health (weekly): - p50 / p95 evolution wall-time - Gate pass rate (per bot) - Cost per evolution (LLM $) - Cost per accepted evolution (efficiency) - Rollback rate (should trend < 5%) - Skill drift: KL-divergence between v0.1.0 and current (safety)

    Ecosystem (quarterly): - GHCR image pulls - GitHub stars / forks - Community-contributed eval sets (count + categories) - Named third-party integrations

    10. Naming rules¶

    Preserve consistency. Reject drift.

    Concept Public / docs Code / packages
    The project evo-skillopt evo-skillopt
    The worker binary evo-skillopt worker worker/skillopt_worker.py
    The vendored algorithm SkillOpt skillopt/

    Rules: - kebab-case in code and package names - Never split into three words in public copy (e.g. "evo skill opt" — no) - Reserve evo- prefix for future sibling projects in the same family that you author yourself — do not use it to imply relationships that don't exist

    11. License & commercialization¶

    This repo: MIT. Everything shipped here is free to self-host, fork, and adapt.

    A commercial hosted offering can layer proprietary code on top — job queue at scale, dashboard UI, reward-model gates, federated learning, enterprise SSO — without contaminating the open core. That layer lives in a separate repo, not here.

    Suggested tier shapes (for anyone building a hosted offering):

    Tier Scope
    Self-host Free · MIT · community support · everything in this repo
    Solo 1 tenant · 1 bot · weekly evolution · hosted worker · basic dashboard
    Team 5 bots · daily evolution · private eval sets · cost dashboard
    Growth 50 bots · hourly cadence · A/B deploy · reward model · HITL queue
    Enterprise Federated meta-skills · SSO · compliance · on-prem · SLA

    Pricing comparables: observability tools (~$40/seat/mo), eval frameworks (~$100/entry/mo), prompt versioning (~$50/seat/mo). evo-skillopt covers the union of those and closes the loop.

    13. Change management¶

    How to update this Blueprint:

    1. Every commit that ships a capability from §5 → tick ⬜ → ✅ and add a one-line changelog entry at the bottom.
    2. Every quarterly review → update §8 roadmap + §9 KPI actuals.
    3. Every new named reference deployment → append to §7 (never delete — history compounds).
    4. Every version tag (v0.2, v0.3, …) → snapshot this file into docs/blueprint-history/vX.Y.md.

    Cadence: - Weekly: tick capabilities - Monthly: KPI actuals - Quarterly: full read-through + roadmap re-plan

    Ownership: this file is the Blueprint. If it disagrees with a decision made in a meeting, either update it same-day or don't make that decision.

    Agent-era GTM (new in v1.2)¶

    Discovery is now a product feature, not a marketing afterthought. Every release ships the agent-SEO stack alongside the code:

    • AGENTS.md at repo root — short, mechanical orientation for coding agents and LLM crawlers.
    • llms.txt + llms-full.txt — llms.txt convention entry points.
    • .well-known/agents.json — machine-readable manifest of endpoints, concepts, and entry points.
    • .well-known/openapi.yaml — OpenAPI 3.1 contract for every endpoint.
    • JSON-LD SoftwareApplication + HowTo + FAQPage in README.md and docs/index.md for AI-search answer engines.
    • CITATION.cff for academic and agent-reference citations.
    • GET /, GET /.well-known/agents.json, GET /llms.txt, GET /openapi.yaml on the live worker — any agent that hits the running service self-discovers capabilities without a trip back to GitHub.

    Why: in the agent era, half the funnel is read by an LLM, not a human. The product that is parseable by an agent wins the agent's citation; the product that is cited by agents wins a funnel it costs nothing to re-fill.

    The full playbook — three audiences (humans, answer engines, agent runtimes), channel mix, metrics, 30-day plan, anti-patterns — lives in GTM.md. Implementation notes on the SEO surface are in docs/AI_SEO.md.
